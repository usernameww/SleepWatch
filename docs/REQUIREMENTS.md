# SleepWatch 核心需求与可靠性设计

> 更新日期：2026-07-23

## 产品目标

SleepWatch 在用户设定的夜间窗口内定时检查手机是否仍在使用。如果设备亮屏且已解锁，则显示休息提醒；如果连续多次检测均未使用，则以第一次未使用检测时间作为入睡时间。主要目标设备为 HyperOS 2 / Android 15，同时兼容 API 26 及以上。

## 监测规则

- 默认窗口为 00:00–05:00，检测间隔 10 分钟，连续未使用阈值 3 次。
- 开始、结束、目标就寝时间、1–60 分钟间隔和 1–10 次阈值均可配置。
- 普通、跨午夜和跨月/跨年窗口使用 `java.time` 统一解析；每晚周期日期创建后不再变化。
- 窗口开始时立即检测。手机“使用中”的定义为 `PowerManager.isInteractive && !KeyguardManager.isDeviceLocked`。
- 使用中检测会提醒，并清空之前的未使用候选；两次检查间收到解锁事件也会清空候选。
- 达到阈值时保存第一次未使用检查的时间，并把状态改为 `SLEEP_CONFIRMED`，当晚不再恢复监测。
- 到结束时间仍未确认时保存 `INCOMPLETE`，不得用结束时间伪造入睡。
- 当晚还支持 `SKIPPED` 和 `ENDED_BY_CONFIG_CHANGE`；已确认、跳过或结束的周期不会重复创建。
- 若进程恢复期间无法确认用户是否解锁，候选序列会保守清零后重新累计，避免误判。

## 调度与后台运行

- 非监测时段不常驻服务，只保留下一次窗口开始闹钟。
- 窗口内由前台服务显示低优先级常驻通知；每次状态落库后再安排下一次检测和窗口结束闹钟。
- 窗口开始、检测和窗口结束使用不同的 `PendingIntent`，重复触发按 `lastCheckTime` 幂等处理。
- 开机、应用更新、系统时间/时区变化和精确闹钟权限变化后执行调度对账。
- 不使用整夜 WakeLock、`START_STICKY` 或 `onTaskRemoved()` 自启动技巧。
- 系统回收、进程终止或划掉最近任务后可由下一次闹钟恢复；用户“强行停止”会进入 Android stopped state，必须重新打开应用，普通应用不能绕过。
- 间隔低于 10 分钟时仍按配置请求调度，但 Doze/厂商省电可能导致延迟。

## 提醒与权限

- 主提醒方式为 `TYPE_APPLICATION_OVERLAY` 全屏悬浮窗；不会主动点亮屏幕，也不会在锁屏状态提醒。
- 同一时刻只保留一个悬浮窗。关闭后到下一检测点才再次提醒。
- 提醒级别按已持久化提醒次数选择；悬浮窗创建失败时降级为高优先级通知。
- 启用监测前必须具备通知、悬浮窗和精确闹钟权限。
- 电池策略“无限制”和 HyperOS 自启动为强提醒项，但不作为程序化硬阻断。
- 前台服务声明 `specialUse` 具体用途；不请求全屏 Intent 或直接忽略电池优化权限。

## 数据与统计

Room 当前版本为 v2，并提供显式 v1→v2 迁移。`SleepRecord` 每个周期唯一，保存：

- 周期状态、窗口开始/结束和具体目标就寝时间；
- 首次提醒、入睡和首次未使用检查时间；
- 连续未使用次数、总检查数、使用中检查数；
- 上次/下次检测、当晚间隔和阈值；
- 提醒次数、评分和创建时间。

旧记录保留睡眠、提醒和评分数据；有 `sleepTime` 的迁移为 `SLEEP_CONFIRMED`，其余为 `INCOMPLETE`。旧记录没有可靠目标时间，因此不重新计算历史达标率。原“紧急事项”字段和偏好数据已移除。

平均入睡、平均评分、达标率和成就只统计 `SLEEP_CONFIRMED`。达标与评分使用记录自身的 `targetBedtimeTime`；跨午夜平均时间采用环形日内时间计算。其他状态在详细记录中单独展示。

## 验收示例

00:00 开始、10 分钟间隔、阈值 3，设备始终未使用时，应在 00:00、00:10、00:20 检测，并最终保存 `sleepTime=00:00`。

发布前需要通过完整 JVM 单测、Room 迁移测试、`assembleDebug` 和零错误 Lint，并在 HyperOS 2 / Android 15 真机连续验证两个夜间周期。
